# BookEat Backend — Architecture

Справочник по устройству бэкенда: компоненты, слои, решения и почему. Не руководство
агенту (это CLAUDE.md) и не список задач (specs/, HANDOFF-файлы) — то, что меняется
от недели к неделе, сюда не входит намеренно.

Фронтенд (apps/mobile, apps/admin, apps/web, дизайн-система) — в отдельном документе
`bookeat-frontend/docs/ARCHITECTURE.md`. Продуктовые требования и бизнес-правила —
в `docs/PRD.md` в этом репозитории.

## Overview

BookEat — платформа бронирования столиков в Казахстане (Алматы, Астана). Гость
ищет заведение, выбирает слот, бронирует, при необходимости платит депозит или
предзаказывает блюда; заведение принимает бронь в своём кабинете и получает
уведомление; платформа ведёт контент (афиша, акции, гастрогид) и рассчитывается
с заведениями.

Одна картинка словами:

```
   Гость                        Персонал заведения           Оператор платформы
     │                                  │                            │
 apps/mobile (Expo/RN)          apps/admin (Next.js)         apps/admin (те же
 apps/web (Next.js)             Telegram mini app            экраны, роль admin)
     │                                  │                            │
     └──────────────┬───────────────────┴────────────────────────────┘
                    │  HTTPS, JSON, /api/v1, Bearer JWT
                    ▼
        ┌───────────────────────────────────────────────┐
        │  Go backend-core (Clean/Hexagonal)            │
        │  cmd/http  — REST API (Gin)                   │
        │  cmd/worker — фоновые задачи (outbox, SLA,    │
        │               реконсиляция, выплаты, синк)    │
        │  cmd/migrate — goose, отдельный шаг деплоя    │
        └───────┬───────────────┬───────────────┬───────┘
                │               │               │
        PostgreSQL 16      Внешние системы   Cloudflare R2
        (единственное      FreedomPay,       (медиа + бэкапы,
         состояние)        TipTopPay,         разные бакеты)
                           Kaspi-сервис,
                           Telegram, WhatsApp,
                           Expo Push, Geoapify,
                           Amplitude, legacy Supabase
```

Отдельно, вне Go-монолита, живёт **Kaspi Pay сервис** (Node + SQLite,
`82.41.30.21`): у Kaspi нет песочницы и устройство привязывается к кассиру, поэтому
он вынесен в самостоятельный мультитенантный сервис и общается с бэкендом по HTTP
и вебхуку.

### Что означает слово «прод»

Исторически «прод» означал две разные системы, и это регулярно путало людей:
старое приложение на Supabase и новый Go-бэкенд. **По проверке 2026-09-02
переключение уже произошло:** гость мобильного приложения ходит в
`backend.book-eat.com` → `213.155.20.76` → контейнер `deploy-postgres-1`
(PostgreSQL 16.6, база `bookeat`); `LEGACY_DB_URL` на проде закомментирован, то
есть боевой контур больше не читает Supabase. На тот момент на проде: goose 103
(88 применённых миграций), 46 заведений, 2462 позиции меню, 128 пользователей,
654 брони, ~23 МБ.

Старый проект Supabase (`wqwpreyqdmifcwftwnwe`) остаётся существовать и содержит
**похожие, но разошедшиеся** данные (44 заведения против 46, разный состав) —
считать его боевым нельзя. Правило: перед любой записью «в прод» сначала доказать
принадлежность базы — сверить `total` публичной выдачи `GET /api/v1/restaurants` и
`md5(description)` одного и того же `id`; совпасть должны и хэш, и счётчик
активных. Один хэш — не доказательство.

Легаси-синк (Supabase → новый Postgres) остаётся включённым **на тесте** и ходит
в офлайн-копию, а не в живую Supabase (см. решения по инфраструктуре).

### Баз данных четыре, не одна

| База | Где | Назначение |
|---|---|---|
| Основная (PostgreSQL 16) | контейнер `deploy-postgres-1` на прод- и тест-сервере | всё состояние Go-бэкенда; схема — миграции goose |
| Legacy Supabase | проект `wqwpreyqdmifcwftwnwe` | старая система; новый бэкенд только читал её односторонним синком, никогда не писал |
| Оффлайн-копия легаси | контейнер `legacy-postgres`, база `legacy_copy` на тесте | тест физически не может дотянуться до боевой Supabase |
| SQLite Kaspi-сервиса | `82.41.30.21`, `/opt/kaspi/app` | свои компании, кассиры, транзакции, вебхуки |

## Backend (Go)

Репозиторий `bookeat-backend`, Go-модуль `backend-core`. Репозиторий **публичный**:
никаких приватных модулей и внутренних библиотек — только публичные модули и
стандартная библиотека. Это ограничение, а не пожелание: если тянет на приватную
зависимость, нужно искать публичный эквивалент.

### Слои и направление зависимостей

Clean/Hexagonal, зависимости смотрят **внутрь**:
`transport → usecase → domain ← infrastructure`.

- **`internal/domain/`** — центр. Плоский пакет, **один файл на сущность**
  (`booking.go`, `payment.go`, `restaurant.go`, …). В файле: структура сущности,
  интерфейс её репозитория, типизированные константы. Никакой бизнес-логики и
  никаких фреймворков (нет импортов gin/sql/http). Статусы и роли — Go-константы
  именованного строкового типа (`type Role string`), в БД хранятся как `VARCHAR`;
  **`CREATE TYPE ... AS ENUM` в миграциях запрещён**. `errors.go` держит sentinel-ошибки
  (`ErrNotFound`, `ErrAlreadyExists`, `ErrForbidden`, `ErrUnauthorized`,
  `ErrInvalidStatus`, `ErrValidation`), от которых зависит маппинг HTTP-статусов.
  `tx.go` объявляет порт `TxManager`.
- **`internal/usecase/`** — прикладная логика, сгруппированная по актору/контексту
  (`admin/`, `bookings/`, `payments/`, `payouts/`, `content/`, `gastroguide/`, …).
  Устоявшаяся форма: экспортируемый интерфейс **`Facade`** с базовыми
  CRUD/чтением, реализованный неэкспортируемой структурой `facade`; зависимости
  передаются **отдельными позиционными аргументами** в `NewFacade(...)` — не
  бандлом `Deps` и не экспортируемым `Service`. Сложные операции получают
  собственный файл и узкий интерфейс рядом с фасадом (`<pkg>/otp.go` →
  `...UseCase`), деление по смыслу, а не по CRUD-глаголу. Логика, общая для
  фасада и отдельного usecase (например выпуск токенов в `auth`), — пакетная
  **свободная функция** над минимальным набором зависимостей, чтобы ни одна
  структура не владела состоянием другой.
- **Порты объявляются там, где потребляются.** У пакета есть `ports.go` с
  интерфейсами внешних систем. Usecase **никогда не импортирует конкретный
  репозиторий чужого домена** — он объявляет свой минимальный порт (interface
  segregation), а связывание с реализацией происходит в `deps.go`. Порты
  транзакций и общесистемных вещей живут в `domain` (`domain.TxManager`).
- **`internal/transport/rest/`** — HTTP-хендлеры на Gin, сгруппированы как
  usecases, плюс общие `middleware/`, `response/`, `httputil/`, `reqlocale/`. На
  ресурс: `handler.go` (зависит от фасада, отдаёт `RegisterRoutes`), `request.go`
  (входные DTO с тегами `validate:"..."`, метод `Validate()`, маппер `ToDomain()`),
  `response.go` (выходные DTO с `fromDomain()`).
- **`internal/infrastructure/`** — реализации доменных интерфейсов, зависят только
  от `domain`. `postgres/<entity>/repository.go` на сущность; HTTP-клиенты внешних
  сервисов — своими подпакетами (`payment/`, `otpsender/`, `telegramnotify/`,
  `whatsapp/`, `expopush/`, `webpush/`, `mediastore/`, `staticmap/`, `amplitude/`,
  `legacysource/`); `sqltx/` — менеджер транзакций.
- **`internal/logger/`** — тонкая обёртка над `log/slog`. Никаких внешних
  логгеров.

**Сборка всего** — `internal/bootstrap/deps.go` (`NewDeps`): единственное место,
где создаются и связываются конкретные репозитории, клиенты интеграций, usecases и
хендлеры. Читать систему нужно отсюда.

### Точки входа

`cmd/http/main.go` — HTTP-сервер. `cmd/worker/main.go` — фоновый воркер.
`cmd/migrate/migrate.go` — goose. Одноразовые: `cmd/etl` (импорт пользователей из
дампа Supabase), `cmd/media-backfill`, `cmd/fpay-probe`, `cmd/hours-probe`. Любая
новая точка входа — тонкая `main`-обёртка: `bootstrap.NewConfig()` → в
`internal/bootstrap`.

### Конфигурация

Полностью на переменных окружения, конфиг-файла нет. Все точки входа читают
`bootstrap.NewConfig()` (`internal/bootstrap/config.go`): env-переменные с
разумными дефолтами, локальный `.env` подхватывается автоматически (настоящие env
побеждают `.env`). Новая настройка = типизированное поле в `Config` + вызов
`getEnv*` в `NewConfig`. `.env` не коммитится никогда.

### Транзакции и работа с БД

Слой БД — **pgx** нативно. `bootstrap.NewDB` возвращает `*pgxpool.Pool`;
репозитории принимают `sqltx.Querier`, который удовлетворяют и пул, и активная
`pgx.Tx`. `bootstrap.NewSQLDB` даёт `database/sql` **только** для goose и
одноразового ETL.

`domain.TxManager` (`WithinTx(ctx, fn)`) реализован `sqltx.Manager`: он кладёт
активную `pgx.Tx` в контекст, вложенные вызовы `WithinTx` переиспользуют уже
открытую транзакцию (двойного `BEGIN` нет). Postgres-репозитории обязаны брать
активный querier из контекста через `sqltx.From(ctx, r.pool)` — иначе операция над
несколькими репозиториями внутри одного usecase разъедется по разным транзакциям.

Репозитории маппят SQLSTATE `23505` (`unique_violation`) в
`domain.ErrAlreadyExists`.

### Ответы и ошибки

Все ответы завёрнуты в `response.Envelope` (`OK` / `Created` / `Error`); каждая
ошибка проходит через `response.HandleError`, который переводит доменные sentinel-ошибки
в статусы 404/409/403/401/422/500. После записи ошибки — немедленный `return`.

Рядом с человекочитаемым `error` в ответе едет машиночитаемый `code`
(`domain.ErrorCode`). **Клиент ветвится по `code`, не по тексту.** По умолчанию —
общий код sentinel-ошибки (`already_exists`, `not_found`, …); когда за одним
статусом прячутся два разных исхода, usecase уточняет код через
`domain.WithCode(...)` — например `slot_taken` против `idempotency_key_reused`,
оба 409 на `POST /bookings`. Добавление кода — аддитивно; изменение или удаление —
ломающее изменение API.

### Аутентификация и роутинг (`bootstrap/app.go`)

- Без аутентификации: `/health` (liveness), `/health/ready` (readiness, пингует
  БД), `/.well-known/jwks.json`. CORS применяется глобально через
  `middleware.CORS` из `APP_CORS_ORIGINS`.
- `/api/*` проходит `middleware.Auth`: снимает `Bearer`, проверяет токен, грузит
  локального пользователя, отклоняет неактивных, кладёт `AuthUser{ID, Role}` в
  контекст (читается `middleware.GetAuthUser`).
- Роль-ограниченные группы — `middleware.RequireRole`; принадлежность к заведению —
  `middleware.RequireRestaurantManager` по `:id` в пути.
- Права на конкретный объект (бронь, отзыв), когда в пути нет id ресторана,
  проверяет **usecase** и отвечает 403 — это осознанный выбор, middleware-гейт там
  неприменим.

### Фоновый воркер

`cmd/worker` — один процесс, внутри независимые горутины-петли (`bootstrap/worker.go`).
Каждая выборка идёт через `SELECT ... FOR UPDATE SKIP LOCKED`, поэтому несколько
инстансов воркера безопасны:

- **booking janitor** — обработка confirm-SLA (авто-подтверждение либо эскалация)
  и закрытие завершившихся броней в `completed` / `no_show`;
- **notification dispatcher** — разбор `booking_outbox`, доставка в каналы (Telegram,
  WhatsApp, mobile push, web push, in-app) c журналом `notification_deliveries`
  против повторной отправки;
- **payments reconciler** — платежи, зависшие в `capturing`/`voiding`/refund;
- **payout reconciler** и **daily payout runner** — сверка и суточная генерация
  выплат;
- **ticket sweeper** — протухшие неоплаченные билеты;
- **event recurrence generator** — генерация дат по правилам серий;
- **analytics dispatcher** — вычитка очередей событий в аналитику;
- **push receipt worker** — квитанции Expo Push;
- **legacy sync** — односторонний импорт из старой системы; дормантен, пока пуст
  `LEGACY_DB_URL`.

Модель доставки — **outbox**: событие пишется в ту же транзакцию, что и сама бронь
или платёж, а разбирает его воркер. У строки очереди есть `attempts`,
`next_attempt_at` (NULL = «можно брать сейчас») и `abandoned_at` — мёртвое письмо,
когда бюджет попыток исчерпан и нужен человек.

### Многоязычность

Ответ локализуется на слое транспорта: `reqlocale.Resolve(c)` определяет
запрошенный язык (явный параметр/заголовок), домен резолвит значение из пары
«базовая колонка + `<имя>_i18n`». Базовая колонка всегда содержит русский текст,
`*_i18n` — карта `{"ru":…,"kk":…,"en":…}`. Набор локалей шире ru/kk/en (есть
ko/zh); добавление новой локали — изменение справочника языков, не схемы.

**Важный контракт:** бэкенд трактует присланную карту `*_i18n` как **полную
замену**, а не как патч. Отсюда жёсткое правило порядка выката (см. решения).

### Конвенции

- **Ошибки:** из usecase и репозиториев наружу идут только доменные sentinel-ошибки;
  SQL- и транспортные ошибки не протекают вверх. Оборачивать через
  `fmt.Errorf("...: %w", err)`, чтобы `errors.Is` продолжал работать.
- **Миграции:** SQL в `migrations/`, формат goose (`-- +goose Up` / `-- +goose Down`),
  встраиваются через `migrations/embed.go`. Перечислимые поля — `VARCHAR` плюс
  валидация в коде. Номера миграций — общий ресурс: две параллельные ветки легко
  берут один номер (уже случалось).
- **Именование:** короткие пакеты в нижнем регистре без подчёркиваний. Интерфейсы
  объявляются у потребителя, не у реализации.
- **Тест-дублёры:** только **руками написанные фейки**, без фреймворков генерации
  моков — чтобы не разрастался набор зависимостей. Фейки лежат в
  `*_test.go` потребляющего пакета (`usecase/auth/fakes_test.go`).
- **Тесты:** табличные, где уместно. Юнит-тесты обязаны проходить
  `go test -short ./...` без внешних сервисов; интеграционные используют
  `infrastructure/postgres/testdb` и включаются переменной `TEST_DATABASE_URL`.
- **Форматирование:** `gofmt -w .` и `go vet ./...` перед завершением любой правки.

Основные команды: `make run`, `make build`, `make tidy`, `make migrate-up`,
`make migrate-down`, `make test`, `make test-short`.

## Kaspi-сервис (Node/SQLite)

Отдельный сервис `kaspi-pos-automation` (форк tapter-dev), развёрнут на
**82.41.30.21** в `/opt/kaspi/app`, systemd-юнит `kaspi.service`, за Caddy на
`https://kaspi.book-eat.com` (basic auth; `/webhooks*` — без пароля). Слушает
`127.0.0.1:3000`, наружу только через Caddy. Совместим с внешней спецификацией
`kaspi.kwaaka.com/docs.html`. Тестовая песочница на том же сервере —
`/opt/kaspi/staging` (тот же код, свой `.env`, порт 3999).

Стек: Node 22 (нужен встроенный `node:sqlite`), Express 4, ESM, без TypeScript.
Локальный Node 20 не подходит — `node:sqlite` там нет, тесты гонять на сервере.

Раскладка: `src/db/` (открытие БД, миграции, `tenant.js`), `src/repo/`
(companies, cashiers, transactions, webhooks, onboarding), `src/tenancy/apiKey.js`,
`src/middleware/` (`apiKeyAuth.js`: `X-Api-Key` → `req.tenant`; `kaspiContext.js`:
кассир → `req.kaspi`), `src/kaspi/` (constants, device, signing, entrance, client,
status), `src/routes/` (`onboard`, `companies`, `v2/payments` + легаси
auth/qr/invoice/history/refund/session), `src/tracker.js` (мультитенантный поллер
статусов и доставка вебхуков), `src/app.js` (сборка Express), `server.js` (только
boot). Панель оператора — серверный рендер без фреймворка (`src/views/`,
`src/routes/admin.js`), живёт **вне `/api/*`**, чтобы её нельзя было принять за
документированный контракт.

Правила, которые держат этот сервис в рабочем состоянии:

1. Никаких глобальных сессий и глобального устройства: всё нужное для запроса в
   Kaspi приходит через `ctx` (устройство + ключ + tokenSN).
2. Любой SQL по данным арендатора — **только через `TenantDb`** (`src/db/tenant.js`),
   который падает, если в запросе нет `company_id`. Прямой `db.prepare` разрешён
   только там, где компания ещё не определена: поиск по api-ключу, по
   onboard-токену и выборка id для фонового воркера.
3. Деньги — целые тиыны (`src/money.js`), комиссия в bps (150 = 1.5 %),
   округление half-up на целых. Наружу отдаются тенге.
4. Секреты в БД только шифрованными (AES-256-GCM, `TOKEN_SECRET_KEY`); API-ключи
   не шифруются, а хешируются SHA-256 — восстановить их нельзя.
5. Транзакции БД не содержат `await`: `node:sqlite` синхронный, `BEGIN` внутри
   одного event loop пересечётся с фоновым воркером.
6. **`KASPI_DRY_RUN=1` — единственный безопасный способ прогонять пайплайн:** у
   Kaspi нет песочницы, каждый счёт и QR — реальные деньги. Кнопки, тратящие
   деньги, требуют `confirm=1` в теле POST.
7. Ротация ключа компании отзывает старый ключ мгновенно — перед ротацией смотреть
   `last_used_at`.

Стык с Go-бэкендом: заведение переключается на Kaspi точечно через
`restaurants.payment_provider = 'kaspi'` плюс запись счёта в
`restaurant_split_accounts`; бэкенд отдаёт админке список компаний
(`GET /api/v1/admin/kaspi/companies`) и принимает вебхук
`POST /webhooks/payments/kaspi` (подпись HMAC; плохая подпись → 401). Kaspi —
одностадийный эквайер, встроенный в двухстадийную машину состояний платежей, что
и делает его особым случаем, а не заменой FreedomPay/TipTopPay.

### Стек на сервере

Одна установка **Docker Compose** на среду, без оркестратора: один скромный VPS на
контур, multi-node сценария нет. Стек в `/opt/bookeat/deploy/docker-compose.yml`:
`postgres` (16.6-alpine, именованный том), `app`, `worker`, `caddy`, плюс сервис
`migrate` под `profiles: ["tools"]`, чтобы обычный `up` его не трогал.
Конфигурация — `/opt/bookeat/deploy/.env` (chmod 600, в git не попадает никогда).

**Один Dockerfile собирает три бинарника** (http/worker/migrate) из одного модуля;
что запускать, решает `entrypoint:` в compose. Один тег образа = одна
консистентная сборка всех трёх.

Порт Postgres наружу не публикуется вообще — подключение только через
`docker compose exec` или SSH-туннель.

Caddy терминирует TLS (Let's Encrypt автоматически), проксирует `app:8080` и
раздаёт статику подпутей на тесте (`/admin-preview`, `/preview`) и
`/web-preview` (reverse_proxy на Node-контейнер сайта).

### Порядок выката

```bash
cd /opt/bookeat/deploy
docker compose up -d postgres          # 1. база первой, дождаться healthy
docker compose run --rm migrate        # 2. миграции ВСЕГДА до рестарта app
docker compose up -d app worker caddy  # 3. приложение
curl -fsS http://127.0.0.1:8080/health # 4. проверка
```

**Миграции — отдельный одноразовый шаг, никогда не часть старта приложения.**
Плохой образ должен откатываться без повторного касания схемы.

CI/CD: `.github/workflows/ci.yml` — build, vet, test, gofmt на PR и push;
`deploy.yml` — сборка образа в GHCR, деплой по SSH, миграции до рестарта,
health-check, автооткат на предыдущий образ. **Тест деплоится автоматически с
`develop`; прод — только `workflow_dispatch` с текстовым подтверждением
`deploy-to-prod`.**

Версионирование образов: неизменяемый тег = 7 символов commit SHA (только он
определяет, что реально бежит), плюс подвижные `current`/`previous` в GHCR для
людей. Источник правды по конкретному серверу — его собственные `IMAGE_TAG` /
`PREVIOUS_IMAGE_TAG` в `.env` и `release-history.log`. Откат образа — одна строка
(`rollback.sh`), **миграции автоматически не откатываются никогда**; миграция без
безопасного `down` откатывается только руками и с явным согласием.

### Выкат фронтенда

Панель и сайт выкладываются **релизами с атомарным переключением симлинка**, а не
`rsync` поверх живого каталога:

```
/opt/bookeat/admin/current -> releases/<release>    # относительный симлинк = корень Caddy
/opt/bookeat/admin/releases/<release>/              # неизменяемые релизы + release.txt
/opt/bookeat/admin/bin/{release.sh,rollback.sh}
```

Проверка после выката — **по содержимому** (`curl .../release.txt`), а не по коду
ответа: SPA-фолбэк отдаёт 200 на любой мусор, включая протухшую сборку. Релизы
обязаны лежать **внутри** смонтированного каталога, иначе Docker не увидит новый
путь.

Пайплайны фронтенда: `deploy-admin-test.yml` и `deploy-web-test.yml` (push в
`develop` по путям + `workflow_dispatch`), скрипты — в `deploy/admin-test/` и
`deploy/web-test/` монорепо. Прод-панель на `admin.book-eat.com` выкладывается тем
же способом, но пока без пайплайна.

### Наблюдаемость

Логи собирает **Grafana Alloy** (не Promtail, не Vector) и шлёт в Grafana Cloud
Loki: app, worker, postgres, caddy, backup. Caddy шлётся полностью (не только
4xx/5xx) — иначе в Loki нет знаменателя для доли ошибок; postgres фильтруется по

норме подолгу молчат, и для них такое правило даёт постоянный ложный сигнал.

## Ключевые архитектурные решения

### Деньги и платежи

- **FreedomPay через Gateway/Sync API, не Invoice v5.** Вся модель расчётов
  двухстадийная (холд → списание при посадке → снятие холда → частичный возврат),
  а Gateway даёт clearing/cancel/refund явными вызовами. Invoice-сценарий не
  закрыт навсегда, но это отдельный адаптер поверх того же порта
  `domain.PaymentGateway`, а не замена. *(ADR-001, подтверждено.)*
- **Реконсилятор платежей: лизинг по времени, без новых статусов.** Зависшие
  `capturing`/`voiding`/refund разбираются по `status_changed_at` (не `created_at`)
  и CAS-обновлениями; внешний вызов эквайера **никогда** не идёт внутри
  транзакции БД. Два инстанса реконсилятора или реконсилятор и вебхук могут
  спросить эквайера про один платёж — побеждает один commit. Осознанный пробел:
  явный «отказ в возврате» сегодня не распознаётся (ни FreedomPay, ни TipTopPay не
  отличают «отказано» от «ещё не записано»), неудавшийся возврат виснет в pending.
  *(ADR-005.)*
- **Выплаты заведениям — раз в сутки по локальному дню площадки.** Одна выплата на
  заведение в сутки, закрывающая последний завершившийся локальный (не серверный)
  день; уникальность держит БД (`uq_payouts_venue_period`), а не код. Причина —
  минимальная комиссия за выплату 300 ₸: выплата по каждой брони разорительна.
  *(ADR-007, подтверждено.)*
- **Комиссию за выплату по умолчанию поглощает платформа** (`PAYOUTS_FEE_BEARER=platform`):
  заведение получает ровно ту сумму, что видело в выписке. Менять дефолт на `venue`
  без нового решения владельца нельзя. *(ADR-007/008, дефолт остаётся открытым
  вопросом самого ADR.)*
- **Порог и удержание выплаты — политика на заведение**
  (`restaurant_payout_settings` переопределяет платформенные 10 000 ₸ / 7 дней),
  писать может только суперадмин: заведению с малым оборотом иначе не выплатили бы
  никогда, но и доверить ему свой порог нельзя. *(ADR-008, подтверждено.)*
- **TipTopPay: сплит в момент оплаты, а не только проводками после.** Доля
  заведения (`base`) и доля платформы (`fee`) делятся на стороне эквайера через
  `Splits`. Причина налоговая: держать чужие деньги на своём счёте — транзитная
  модель, от которой ушли осознанно. Заведение без активного идентификатора
  эквайера **не может принять оплату вообще** (503), а не «принять и разобраться
  потом». *(ADR-020; отправка сплитов через `/orders/create` пока выключена флагом —
  документация провайдера не подтверждает поле.)*
- **Налоговая рамка:** ОУР + агентский/комиссионный договор, доход платформы =
  только комиссия, доля ресторана — транзит; статус резидента Astana Hub. На
  упрощёнке комиссионер платит налог со всего оборота — ловушка для маркетплейса с
  высоким GMV. *(Консультационная ориентировка, требует подтверждения налогового
  консультанта РК.)*
- **Предзаказ у подтверждённой брони: гостю нельзя, персоналу можно.** После
  `confirmed` состав меняет только заведение или админ (`preorder_locked`); кухня
  уже готовит. Терминальные статусы закрыты для всех. *(ADR-030.)*
- **Леджер пишется только там, где реально двигаются деньги:** `created→failed`,
  `authorized→voided`, `authorized→expired` проводок не создают (только
  outbox-событие); проводки идут на `captured` и на `Settle`. Домен запрещает
  пустой леджер-батч, а типов «hold»/«void» в `LedgerEntryType` нет.
- **Kaspi Pay — отдельный путь, а не третий адаптер внутри Go.** Причины: нет
  песочницы, устройство привязано к кассиру. Изоляция арендаторов — в слое данных
  (`TenantDb`), не в хендлерах. *(ADR-031/032/034.)*
- **Канонический провайдер по умолчанию не назван** — это зафиксированное
  противоречие: одновременно живут FreedomPay (дефолт в `payment_providers`),
  TipTopPay (стратегическое направление после налогового анализа) и Kaspi
  (точечно per-restaurant).


### Бронирование

- **Table-less режим:** заведение может объявить вместимость в одновременных
  гостях (`booking_capacity_mode='seats'`) вместо списка столов; защита от
  овербукинга — в БД, бакетами по 15 минут и `CHECK(seats_taken <= seats_limit)`.
  Причина: у большинства заведений столы не заведены вообще, а GiST-exclusion по
  столам там ничего не защищает. Режим включается **осознанно** через админ-API,
  дефолт всегда `tables` — молча никого не переключаем. *(ADR-009, подтверждено.)*
- **Осознанный овербукинг — отдельный флаг `overbook`, не `force`.** `force` в
  режиме столов значит «посади за ЭТИ столы»; клиент, шлющий `force: true` по
  привычке, начал бы молча овербукить. Овербукинг виден счётчику мест, аудируется
  append-only таблицей, лимит бакета перештамповывается и не наследуется следующей
  обычной бронью. Поднимать `booking_capacity_seats` «временно» нельзя — это тихо
  продаёт лишние места всем и навсегда. *(ADR-011, подтверждено.)*
- **Спецдни авторитетны для обеих сторон** — и для витрины/`open_now`, и для
  движка доступности. Раньше их читал только денежный путь, из-за чего заведение,
  закрытое на праздник, показывалось открытым и продавало слоты. *(ADR-014.)*
- **Движок читает спецдни в окне вокруг запрошенной даты, не вокруг «сейчас»** —
  иначе ломается правка старой брони. Кабинет заведения видит все спецдни без
  ограничений. *(ADR-015.)*
- **Поиск — Postgres full-text, без Elasticsearch.** Десятки заведений не
  оправдывают второй поисковый движок и его эксплуатацию.


### Авторизация и OTP

- **Водопад доставки кода: Telegram Gateway → WhatsApp → SMS.** Канал существует
  тогда и только тогда, когда заданы его креды (отдельного флага «включено» нет);
  порядок — по цене ошибки. **Память канала по номеру пишется только после
  верификации кода**, не после «принято провайдером» (Meta отвечает 200 на номер
  без WhatsApp). Эндпоинт не должен становиться оракулом «есть ли у номера
  Telegram» — коды ошибок по каналам не различаются. *(ADR-010.)*
- **Тестовый аккаунт для App Review — серверный**, фиксированный номер и код через
  env; при выключенных переменных номер не существует как особый случай. Скрытый
  вход в клиенте (долгое нажатие по логотипу) отклонён: Apple Guideline 2.3.1
  прямо запрещает скрытую функциональность. *(ADR-025.)*
- **Счётчик попыток OTP не атомарен** — известный осознанный долг: чтение
  `Attempts` и инкремент не в одной транзакции. Правильный фикс правит общий путь
  логина, поэтому его нельзя вшивать в фичевый PR; сегодня риск снижен рейт-лимитом
  5 запросов/мин/IP. Закрытой эту дыру считать нельзя.
- **Код OTP в лог — только при `APP_ENV=development`.** «Одноразовый код в логах
  равен угону аккаунта».
- **Вход в кабинет — email + пароль, вход гостя — OTP.** Унифицировать без
  выяснения исходной причины не нужно.


### Инфраструктура и выкатка

- **Docker Compose на каждом сервере, не Kubernetes** — нет multi-node сценария,
  который оправдал бы накладные расходы.
- **Один образ, три бинарника** — один тег = одна консистентная сборка.
- **Миграции — отдельный шаг, не часть старта приложения** — чтобы плохой образ
  откатывался без касания схемы.
- **Бэкапы: pg_dump + офсайт-копия в R2 через rclone, не restic.** Локальная копия
  не защищает от потери сервера целиком; restic добавил бы дедупликацию и
  шифрование, которых не просили и которые усложнили бы восстановление «скачать
  один файл» в стрессе. Публичный домен на бакете с бэкапами — запрещено при любых
  обстоятельствах. *(ADR-003.)*
- **Логи: Grafana Alloy, не Promtail (deprecated) и не Vector**; caddy шлётся
  полностью, иначе нет знаменателя для доли 5xx. *(ADR-004.)*
- **Алерт «сервис молчит» — только на caddy**, потому что тишина app/worker — норма.
- **Панель на тесте: статический экспорт по подпути, тот же origin** — без
  отдельного Node-процесса и без правки CORS. Вариант перестанет работать сам,
  если в панели появится SSR или route handlers — тогда разговор о контейнере
  вернётся осознанно. *(ADR-006.)*
- **Веб-сайт, наоборот, Node-контейнер**, а не статика: динамический
  `app/venues/[id]` без `generateStaticParams` статикой не собирается. *(ADR-035.)*
- **Выкат панели: релизы + атомарный симлинк, проверка по содержимому.**
  `rsync --delete` поверх живого каталога отдаёт гостю смесь старых и новых
  файлов; проверять успех по HTTP-коду бессмысленно из-за SPA-фолбэка.
  *(ADR-018 / ADR-024.)*
- **Тестовый контур ходит только в офлайн-копию легаси-БД.** 26.07.2026 агент
  реально создал таблицу в живой легаси-базе, проверяя, заблокирована ли запись:
  «только чтение» держалось на дисциплине кода (`SET default_transaction_read_only`),
  а не на правах роли, и через Supavisor-пулер молча игнорировалось. Подключать
  тест или dev к боевой Supabase нельзя ни под каким предлогом. *(ADR-014.)*
- **Статичная карта — прокси на бэкенде по ID заведения**, ключ провайдера только
  в env сервера: ключ из APK/IPA достают за минуты, а приём сырых координат
  превратил бы ручку в открытый прокси картинок для всей планеты. Размер и зум — по
  белому списку. Провайдер — Geoapify (коммерческое использование разрешено), 2ГИС
  как цель на будущее; MapTiler на бесплатном плане запрещает коммерческое
  использование. *(ADR-012, ADR-033.)*


### Интеграции

- **Kwaaka Table Booking API:** реальный путь `/v1/table-booking` (не `/api/v1` из
  их swagger), формат ошибки `{"message":...}`; Kwaaka подтвердила, что чинить
  будет документацию, а не сервер. Машиночитаемых кодов ошибок нет — маппинг по
  подстрокам. Запись брони через Kwaaka **не реализована**, была только разведка на
  чтение.
- **Панель оператора Kaspi считает межкомпанийную статистику построчно через
  `TenantDb` (N+1), а не одним кросс-тенантным SQL** — ровно ради того риска
  утечки между арендаторами, против которого обёртка и создавалась. *(ADR-032.)*
- **WhatsApp-бот поддержки: рекомендован, не построен.** No-code SaaS (Wati и
  подобные) рассмотрен и отклонён.


### Не решено и противоречиво (состояние, а не решение)

- **Лояльность сломана, решение не принято.** Две параллельные валюты (`stamps` и
  `points`) без ясности, какая главная; награды глобальные, а не per-restaurant;
  ни одного погашения ни разу не было. Корень проблемы — схема не знает, **кто
  финансирует награду**. «Просто включить редемпшн» без ответа на этот вопрос —
  тот же баг на новом месте.
- **Канонический платёжный провайдер для нового заведения не назван** (см. выше).
- **OTP-водопад построен дважды независимо** — в старой Supabase-функции и в новом
  Go-бэкенде; решения о выключении одного из них нет.
- **Дубли заведений в `restaurants`** (два «Dostyk Plaza», два «Panfilov») и два
  семейства UUID (настоящие и seed-стиля `0ceab001-0000-...`) — правило слияния не
  определено.

### Общая картина

PostgreSQL 16, схема `public`, расширения `btree_gist` и `pg_trgm`. На тесте на
30.08.2026: 88 таблиц, 271 индекс, 129 внешних ключей, 115 CHECK-ограничений,
22 уникальных, 3 ограничения непересечения. Самая большая таблица — `menu_items`.
**Ни одного настоящего Postgres-enum нет:** все статусы — `varchar`, часть закрыта
CHECK, часть валидируется только в Go.

Шесть смысловых групп:

1. **Пользователи и доступ** — `users` (единая карточка гостя, сотрудника и
   админа; `role` = `user`/`restaurant`/`admin`), `user_credentials` (bcrypt,
   1:1, есть только у входящих по паролю), `refresh_tokens` (хранится
   `token_hash`), `otp_codes` (`code_hash`, `attempts`, `used_at`, `channel`),

### Инварианты, которые держит база

- **Пересечение броней по столу физически невозможно.** `booking_tables.slot` —
  диапазон `tstzrange`, поверх него GiST-ограничение непересечения. Не проверка в
  коде — ограничение в БД. Ещё два таких ограничения на `external_reservations`.
- **Овербукинг в режиме мест невозможен.** `restaurant_capacity_buckets` хранит
  проданные места по 15-минутным бакетам, `CHECK (seats_taken <= seats_limit)`
  физически отказывает; сама строка бакета служит замком, на котором
  сериализуются две одновременные брони.
- **`booking_tables.active` и `booking_capacity_holds.active` приложение не пишет
  никогда.** Значение выводится из статуса брони: на INSERT, повторно на COMMIT
  пишущей транзакции и триггером при смене статуса. Стол считается занятым в
  статусах `pending`, `confirmed`, `arrived`.
- **Деньги сходятся:** `payments.amount_minor = base_amount_minor + fee_minor`
  (CHECK); платёж относится ровно к одному предмету — либо бронь, либо билет
  (CHECK); `event_tickets.total_minor = unit_price_minor * quantity` (CHECK).
- **Сумма проводки всегда положительна**, знак несёт `direction`
  (`debit`/`credit`).
- **Цена предзаказа фиксируется в момент заказа** (`booking_items.item_price_minor`),
  как и правила возврата билета (`refund_policy_*` копируются на момент покупки) —
  чтобы позднее изменение меню или политики не переписало условия задним числом.
- **Журнал посадок сверх вместимости — append-only:** триггер запрещает UPDATE и
  DELETE на `booking_capacity_overrides`.
- **Идемпотентность повторов** держат уникальные пары: (провайдер,
  `provider_event_id`) в `payment_events`, (`outbox_event_id`, `user_id`) в
  `notifications`, `uq_payouts_venue_period` в `payouts`,
  `payments.idempotency_key`.

### Статусы (enum'ов в БД нет)

- **Бронь** `bookings.status`: `pending`, `waitlist`, `confirmed`, `arrived`,
  `completed`, `cancelled`, `no_show`. Разрешённые переходы:
  `pending → confirmed / waitlist / cancelled`; `waitlist → confirmed / cancelled`;
  `confirmed → arrived / cancelled / no_show`; `arrived → completed / cancelled`.
  **`no_show` достижим только из `confirmed`** — это нарушенное обещание, которое
  заведение приняло. Неотвеченную бронь фоновый воркер закрывает как `cancelled`
  с `cancelled_by = system`.
- `bookings.source`: `app`, `admin`, `phone`, `widget`.
  `bookings.cancelled_by`: `guest`, `restaurant`, `system`.
- **Платёж** `payments.status`: `created`, `authorized`, `capturing`, `captured`,
  `voiding`, `voided`, `partially_refunded`, `refunded`, `failed`, `expired`.
  `purpose`: `deposit`, `preorder`, `ticket`.
- **Возврат** `payment_refunds.status`: `created`, `in_flight`, `succeeded`,
  `failed` (плюс `pending` в коде). **Выплата** `payouts.status`: `pending`,
  `sent`, `paid`, `failed`.
- **Бухгалтерия:** `account` = `guest`/`restaurant`/`platform`/`acquirer`;
  `direction` = `debit`/`credit`; `entry_type` = `capture`, `service_fee`,
  `refund`, `acquiring`, `settlement`, `correction`.
- **Роли:** `users.role` = `user`/`restaurant`/`admin`;
  `restaurant_managers.role` = `owner`/`manager`/`hostess`.
- **Каналы уведомлений:** `web_push`, `telegram`, `mobile_push`, `in_app`,
  `whatsapp`. **Каналы OTP:** `telegram_gateway`, `whatsapp`, `sms`, `stub`,
  `undelivered`. **Эквайеры:** `freedompay`, `tiptoppay`, `partnerspay`, `kaspi`.
- **Контент:** у `events` и `promos` **два независимых статуса**, и их постоянно
  путают: `status` (`draft`/`published`/`hidden`) — видимость самой карточки, а
  `feed_status` (`not_submitted`/`pending_review`/`approved`/`rejected`) —
  отдельная модерация показа в ленте главной. Опубликованное событие с
  `not_submitted` живёт на странице заведения, но на главную не попадает.

### Многоязычность в схеме

Рядом с обычной колонкой лежит `<имя>_i18n` типа `jsonb` вида
`{"ru":…,"kk":…,"en":…}`. **Базовая колонка всегда содержит русский текст.**
Чтение сначала смотрит в карту, при отсутствии перевода падает обратно на колонку.
Инвариант «значение по ключу `ru` равно базовой колонке» держит **код записи, а не
база**: CHECK намеренно нет, иначе любая уже разошедшаяся строка превращала бы
редактирование в 500. `NULL` в `*_i18n` = «переводов нет, показываем русский».
Пары есть у `restaurants`, `menu_items`, `events`, `promos`, `event_recurrences`,
`restaurant_stories`, `gastro_routes`, `gastro_route_points`, `gastroguide_*`,
`cities`, `cuisines`, `venue_features`, `menu_categories`.

`menu_items.language` — **не** фильтр чтения, а ярлык языка самой строки. Гостю
всегда отдаются базовые строки, локализованные из `*_i18n`.

### NULL как «политика платформы»

В `restaurants` вся политика броней и почти вся политика денег — **необязательные
переопределения**. NULL означает не «ноль» и не «выключено», а «взять значение
платформы из переменных окружения»: `booking_duration_minutes`,
`booking_buffer_minutes`, `booking_lead_minutes`, `booking_horizon_days`,
`cancel_deadline_minutes`, `confirm_sla_minutes`, `max_guests_per_booking`,
`auto_confirm`, `confirm_on_create`, `payments_enabled`, `deposit_required`,
`preorder_payment_required`, `service_fee_bps`, `payment_provider`.
`booking_capacity_mode = NULL` равнозначно `tables`. То же правило в
`restaurant_payout_settings`: нет строки или NULL в колонке = политика платформы.

`auto_confirm` и `confirm_on_create` — **разные вещи**: `confirm_on_create`
подтверждает бронь сразу при создании, `auto_confirm` решает, что делать, когда
истёк срок ответа заведения.

`events.city` / `promos.city` = NULL имеет **два разных смысла**, и различает их
наличие `restaurant_id`: при наличии заведения — «город берём у заведения», у
контента платформы — «во всех городах».

### Флаги, которые легко перепутать

- `restaurants.is_active = false` — мягкое удаление: заведение пропадает из
  каталога **и** перестаёт открываться по прямой ссылке (404).
- `restaurants.hidden_from_home` — убрано только с главной; в каталоге, поиске и
  по прямой ссылке остаётся.
- `restaurants.is_new` / `is_popular` / `is_premium` — **nullable boolean**, то
  есть три состояния (да/нет/не задано).
- `restaurant_stories.image_url` — адрес картинки, `action_url` — куда ведёт тап.
  Похожие имена, разные вещи; `action_url` ограничен схемой http/https через CHECK.

### Мягкие удаления и ссылочная целостность

`users.deleted_at` + обнуление личных полей + `is_active = false` одной записью.
Строка остаётся, чтобы брони и платежи не потеряли ссылку; телефон и почта уходят
именно в **NULL**, а не в заглушку — обе колонки уникальны, а два NULL в Postgres
не равны, значит номер сразу свободен для новой регистрации. Аналогично:
`restaurants.is_active`, `restaurant_tables.is_active`,
`device_push_tokens.is_active`, `booking_blacklist.is_active`,
`reviews.status='hidden'`, `telegram_staff_links.revoked_at`,
`refresh_tokens.revoked_at`. Настоящего `DELETE` почти нет; внешние ключи
настроены осознанно: `CASCADE` для спутников, `SET NULL` для истории, `RESTRICT`
для всего, что связано с деньгами.

### Деньги и время

- **Деньги везде целые в минорных единицах** (`*_minor`, тиыны), валюта отдельной
  колонкой `currency` (везде `KZT`). **Единственное исключение —
  `menu_items.price` типа `numeric(12,2)`**; это известная несогласованность.
- Часы работы (`restaurant_working_hours.open_time`/`close_time`, переопределения,
  `restaurant_time_slots`) хранятся **строкой `HH:MM`**, а не типом `time`.
- `restaurants.timezone` на тесте был NULL у всех заведений, то есть фактически
  работало запасное значение из кода — при появлении заведения вне Алматы/Астаны
  это выстрелит.

### Триггеры и функции

9 триггеров и 15 функций. Существенные:

- `trg_restaurants_sync_city`, `trg_events_sync_city`, `trg_promos_sync_city` —
  подставляют `city_id` по написанию города через `city_aliases`.
- четыре триггера поддерживают `active` в `booking_tables` и
  `booking_capacity_holds` в соответствии со статусом брони;
- `trg_booking_capacity_holds_sync` пересчитывает `restaurant_capacity_buckets`;
- `trg_capacity_overrides_append_only` запрещает изменять и удалять журнал
  посадок сверх вместимости;
- `restaurant_search_text` и `menu_item_search_text` собирают документ для
  полнотекстового поиска и триграммных индексов — **ссылаться на выражение в
  запросе надо дословно**, иначе индекс не применится.

### Наследие, которое ещё живо

Кандидаты на удаление и подозрительные места (полный разбор — в разделах 4–5
исходного файла): `restaurant_categories` (заменён `cuisines` миграцией 0079),

## API

Полный список из 285 маршрутов с указанием авторизации и реального потребителя:
**`/home/tai/work/bookeat-knowledge/02-api-map.md`** (снят с `develop`, коммит
`a1305de`, 29.08.2026). Ниже — форма контракта.

### Пути и версионирование

- **`/api/v1` есть почти у всего, но не у всего.** Вне префикса живут вебхуки
  эквайеров (`/webhooks/payments/...`) и служебные `/health`, `/health/ready`,
  `/.well-known/jwks.json`, `/docs`.
- Единая точка сборки роутера — `internal/bootstrap/app.go`, дальше по методам
  `RegisterRoutes` / `RegisterPublic` / `RegisterAdminRoutes` в
  `internal/transport/rest/*`.
- Swagger UI на `/docs` (+ `/docs/openapi.yaml`, `/docs/openapi.json`)
  монтируется **только вне production**.
- Версия одна — `v1`. Совместимость поддерживается аддитивно: новый `code` ошибки
  или новое поле — можно, изменение или удаление существующего — ломающее
  изменение.

### Уровни авторизации

| Уровень | Что значит |
|---|---|
| публично | без токена вообще |
| публично (токен опционально) | `OptionalAuth`: без токена работает, с токеном дорисовываются персональные поля (`is_favorite`) |
| токен | нужен Bearer, действие над своими данными |
| токен + RBAC | нужен Bearer, право на конкретный объект проверяет usecase и отвечает 403 |
| менеджер заведения | middleware `RequireRestaurantManager` по `:id` в пути |
| суперадмин | middleware `RequireRole(admin)` |
| вебхук-подпись | без токена, подлинность по подписи или секретному заголовку |

**Префикс `/admin/` в пути не означает «только суперадмин»** — больше половины
таких путей доступны менеджеру конкретного заведения. Кто реально пускает,
определяется middleware и usecase, а не формой пути.

### Группы ручек

- **Авторизация** — вход по паролю (`/auth/login`, `/auth/signup`), по коду на
  телефон (`/auth/otp/request`, `/auth/otp/verify`), `/auth/refresh`,
  `/auth/logout`, ветка входа персонала через Telegram mini app
  (`/auth/telegram/*`), смена телефона в профиле (тоже через OTP).
- **Профиль гостя** — `/users/me` (GET/PATCH/DELETE), аватар, согласия,
  настройки уведомлений.
- **Каталог** (всё, что видно до брони) — список и поиск заведений, карточка,
  подборка «Выбрали для вас» (`/restaurants/picks`), лента главной (`/feed`),
  меню и его хайлайты, сторис, отзывы и агрегированный рейтинг, события и акции,
  гастрогид (подборки, рубрики, статьи, гастропрогулки), картинка карты
  (`/restaurants/:id/map` — прокси), справочники городов, кухонь и удобств.
  Читается анонимно, часть с `OptionalAuth`.
- **Избранное** — заведения, события, акции (три параллельных набора ручек плюс
  общий `/favorites/items`).
- **Уведомления и устройства** — push-токены телефона, web-push подписки
  персонала, лента уведомлений гостя.
- **Бронирование, гость** — календарь слотов (`/restaurants/:id/availability`),
  `POST /bookings` (строгий rate limit + идемпотентность), список своих броней,
  перенос, отмена, история статусов, чат по брони, анкета после визита, предзаказ,
  лист ожидания.
- **Бронирование, заведение** — подтверждение/отклонение/приход/закрытие/неявка,
  календарь заведения, ручная бронь от хостес, стоп-лист гостей, политика брони,
  внешние блокировки мест, переопределения вместимости.
- **Платежи и билеты** — создание платежа по брони и ссылка на оплату, статус,
  доплата (`settle`), `capture`/`void` холда, покупка и возврат билетов, выплаты
  заведениям (реквизиты, настройки, генерация и отправка — **эти три помечены
  «деньги наружу»**), список компаний Kaspi-сервиса.
- **Контент** — сторис, акции, события и правила серий, лента главной с
  модерацией, очередь черновиков, редакторский кабинет гастрогида, загрузка
  картинок в R2 (`POST /admin/media/images`).
- **Панель платформы** — все заведения, справочники городов/кухонь/удобств,
  подборка главной, роли пользователей, платформенный дашборд, очереди модерации.
- **Вебхуки** — три платёжных (`/webhooks/payments/freedompay` — подпись `pg_sig`,
  ответ XML; `/webhooks/payments/tiptoppay/:type` — HMAC в заголовке;
  `/webhooks/payments/kaspi` — подпись, плохая → 401) и два телеграмных
  (`/api/v1/telegram/webhook` — старый бот, `/api/v1/telegram/staff-webhook` —
  `@book_eat_restaurants_bot`). Оба телеграмных требуют секретный заголовок и без
  секрета в конфиге отвечают 404.
- **Служебные** — `/health`, `/health/ready`, JWKS, Swagger UI.

### Что важно знать про эту карту

- На 29.08.2026 из 285 маршрутов у **93** не нашлось ни одного вызова из
  фронтенд-монорепо. Это **не** доказательство смерти: ручку может звать внешний
  интегратор, Telegram mini app (живёт вне монорепо), старая админка или ещё
  ненаписанный экран. Пять из этих 93 — вебхуки, у которых вызывающий заведомо
  внешний.
- В API есть **осознанные дубли путей**: например меню-ручки существуют и под
  `/admin/restaurants/:id/...`, и под `/restaurants/:id/...`; админка ходит по
  одному из двух. Прежде чем «унифицировать», нужно проверить, кто ходит по
  каждому.
- Форма ответа всегда конвертная (`data` / `error` + `code`); клиент ветвится по
  `code`.

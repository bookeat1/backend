# TipTop Pay — сплитование платежей

Что уже сделано в коде, что нужно от TipTop Pay и от оператора, и какие вопросы
остаются открытыми. Источник: https://developers.tiptoppay.kz, раздел
«Сплитование платежей», версия документа 1.0.2 от 23.04.2025 (прочитан
20.08.2026).

## Что такое сплит у нас

Гость платит одну сумму. Эта сумма уже сегодня делится на две части:

| Часть | Поле платежа | Кому | Где это видно сейчас |
|---|---|---|---|
| База (депозит / предзаказ / билет) | `payments.base_amount_minor` | заведению | проводка `restaurant` в `payment_ledger_entries` |
| Сервисный сбор | `payments.fee_minor` | платформе | проводка `platform` |
| Итого списывается с гостя | `payments.amount_minor` | — | — |

Сплит не вводит вторую комиссию. Он просит эквайера сделать **то же самое
деление в момент оплаты**: доля заведения уходит на его саб-мерчанта, наша — на
наш, вместо того чтобы вся сумма легла на наш счёт и разъезжалась потом
выплатами (`usecase/payouts`).

Модель: `domain.PaymentSplitPlan` (`internal/domain/payment_split.go`).
Всё в целых тиынах; десятичная строка с точкой и двумя знаками появляется
только на границе адаптера (`payment.FormatMinor`).

## Что требуется от TipTop Pay (мы этого пока не имеем)

1. **Подключить продукт «Сплитование платежей» на терминал.** Документация:
   «необходимо подать заявку своему персональному менеджеру». Само по себе
   интеграцией не включается. Без этого любой запрос со `Splits` получает
   `Split transaction is not supported`.
2. **Завести каждое заведение саб-мерчантом** под нашим терминалом-маркетплейсом
   и получить его `PublicId` из личного кабинета. **На 20.08.2026 такого
   идентификатора нет ни у одного заведения.**
3. **Наш собственный `PublicId` саб-мерчанта** — куда падает комиссия
   платформы. Сумма всех `Splits.Amount` обязана равняться `Amount` запроса, то
   есть нашу долю тоже нужно адресовать явно.
4. **Совпадение режимов терминалов** маркетплейса и саб-мерчантов, иначе
   `Split transaction error. Terminals modes not equal`.
5. **Шлюз, поддерживающий сплит, на стороне эквайера** — иначе
   `Split transaction is not supported on the Acquirer side` (ErrorCode 6018).
6. Если когда-нибудь понадобится фискализация — данные чека передаются
   отдельно по каждому `Splits.JsonData` (обёрнутые в объект `PaymentData`).
   Кассы у нас нет, поэтому `JsonData` не отправляется вовсе.

## Что нужно сделать оператору, когда идентификаторы появятся

1. **Наш саб-мерчант.** Прописать в окружении сервиса:
   `PAYMENTS_PLATFORM_SPLIT_ACCOUNT=<наш PublicId саб-мерчанта>`.
2. **Идентификатор заведения.** Одна строка в `restaurant_split_accounts`
   (миграция 0077) на пару (заведение, эквайер):

   ```sql
   INSERT INTO restaurant_split_accounts (restaurant_id, provider, account_ref, is_active)
   VALUES ('<uuid заведения>', 'tiptoppay', '<PublicId саб-мерчанта>', true)
   ON CONFLICT (restaurant_id, provider)
   DO UPDATE SET account_ref = EXCLUDED.account_ref, is_active = true, updated_at = now();
   ```

   Отдельного экрана в админке пока нет — это осознанный пропуск, см. «Чего ещё
   нет». Отключить заведение от сплита можно, поставив `is_active = false`;
   строка при этом сохраняется, и видно, куда уходили прошлые платежи.
3. **Включить сплит:**
   `PAYMENTS_SPLIT_ENABLED=true` (решение усечения на стороне бизнес-логики) и
   `TIPTOPPAY_SPLITS_ENABLED=true` (терминал действительно умеет сплит).
   Включать только после шага 1 и 2 хотя бы для одного заведения:
   **с включённым сплитом заведение без идентификатора вообще не сможет принять
   оплату** — оно получит отказ с кодом `split_account_missing` (HTTP 503).
   Это сделано намеренно (решение владельца, 20.08.2026): деньги, ушедшие не
   туда, разбирать дороже, чем отказать сразу.
4. **Как проверить, что сплит поехал.** Порядок, от дешёвого к дорогому:
   - в логах создания платежа есть поле `split_shares` (только количество долей,
     сами `PublicId` в логи не попадают никогда) — на сплитованном платеже оно
     равно 2;
   - `POST /payments/get` по транзакции возвращает массив `Splits` ровно в том
     виде, в каком мы его отправили. Если массива нет — сплит не применился,
     деньги ушли одному получателю;
   - в личном кабинете TipTop Pay операция видна у обоих саб-мерчантов;
   - подтверждение и возврат тоже несут `Splits` (см. ниже) — проверить, что
     после `confirm` доли не «схлопнулись» в одну.

## Что уже умеет код

- `Authorize` кладёт массив `Splits` в запрос; суммы валидируются до вызова
  провайдера (сумма долей = сумма платежа, доля положительная, `PublicId` есть и
  не повторяется, долей не больше `domain.MaxPaymentSplits`).
- `Capture` (`/payments/confirm`) и `Refund` (`/payments/refund`) сначала читают
  исходные доли из `/payments/get` и повторяют их. Это требование документации:
  доля, не перечисленная в `confirm`, **отменяется целиком**, а возврат без
  `Splits` отвечает `Field "Splits" is required`.
- Частичное подтверждение/возврат делит доли пропорционально по методу
  наибольших остатков — сумма долей всегда точно равна подтверждаемой сумме, ни
  одного тиына не теряется и не появляется.
- `Void` не изменён: отмена по документации снимает все доли сразу.
- Ошибки сплита от провайдера маппятся в наши коды (`split_not_supported`,
  `split_submerchant_unknown`, `split_terminal_mismatch`, `split_sum_mismatch`,
  `split_account_duplicate`, `split_required`, `split_amount_too_big`).

## Открытые вопросы — проверить на песочнице до боевого включения

1. **`/orders/create` и `Splits` — главный.** Документация перечисляет сплит для
   `/payments/cards/{charge,auth}` и `/payments/tokens/{charge,auth}`. Метод
   `/orders/create`, которым мы создаём платёжную страницу, в списке **не
   значится**, и в его таблице параметров поля `Splits` нет. Мы не знаем,
   принимает ли он этот массив или молча игнорирует. Игнорирование — самый
   дорогой сценарий: гость платит правильную сумму, а доля заведения оседает у
   платформы. Поэтому отправка `Splits` через order-флоу закрыта отдельным
   флагом `TIPTOPPAY_SPLIT_VIA_ORDERS`, по умолчанию выключенным; с
   выключенным флагом сплитованный платёж не создаётся вовсе (`split_flow_unsupported`).
   **Спросить менеджера:** поддерживает ли `/orders/create` сплит, и если нет —
   какой метод использовать вместо него (переход на криптограмму/виджет означает
   фронтовую работу и заход в PCI-периметр, которого мы сейчас избегаем).
2. **Частичное подтверждение.** Документация говорит только «не больше, чем было
   на оплате, по каждому `PublicId`». Как делить уменьшение между заведением и
   платформой — не сказано. Мы делим пропорционально; бизнес может захотеть
   «сначала уменьшается доля заведения». Помечено `TODO(verify)` в
   `internal/infrastructure/payment/tiptoppay/split.go`.
3. **Возврат по авторизованному (не подтверждённому) сплиту** документация
   запрещает («Невозможно выполнить возврат» — надо делать `void`). Наш
   `RefundUseCase` возвращает деньги только из `captured`, так что попасть туда
   не должен, но на песочнице стоит убедиться.
4. **Комиссия эквайера при сплите.** Непонятно, удерживается ли она с каждой
   доли отдельно или с общей суммы. От этого зависит, остаётся ли верной наша
   формула gross-up (`domain.GrossUpForAcquirerWithMinimum`), которая
   рассчитывает сбор так, чтобы заведение получило базу целиком.
5. **Уведомления.** В callback (`Check`, `Pay`, `Confirm`, `Refund`, `Fail`,
   `Cancel`) приходит массив `Splits`. Сейчас вебхук его не разбирает — это
   безопасно (сумма и статус берутся из основных полей), но сверять доли по
   уведомлению было бы полезно.

## Доступы для песочницы

Для живого вызова нужна **пара** Public ID + API Secret (Basic-авторизация:
логин = Public ID, пароль = API Secret) — плюс включённый на терминале сплит и
минимум два `PublicId` саб-мерчантов, иначе сплит проверить нечем.

Переданный тестовый токен — одна 32-символьная строка, и чем именно она
является, не указано. По форме это больше похоже на API Secret (Public ID у
TipTop Pay выглядит как `pk_…` или `test_api_…`), но это догадка. Нужно
запросить недостающую половину пары и подтвердить, какая из них какая.

Ни один из этих ключей не должен попадать в репозиторий, в тесты и в лог: они
читаются только из окружения (`TIPTOPPAY_PUBLIC_ID`, `TIPTOPPAY_API_SECRET`).

## Чего ещё нет

- **Экрана в админке** для ввода `PublicId` заведения — сегодня это INSERT
  руками (см. выше). Осознанно: пока идентификаторов нет ни у кого, форма
  ввода была бы формой ввода пустоты. Как только заведения начнут подключаться
  пачками, это первое, что стоит добавить.
- **Сверки долей по уведомлениям** (см. открытый вопрос 5).
- **Сплита для оплаты билетов** (`usecase/payments/ticket.go`) — там своя
  авторизация, и она пока сплит не строит.
